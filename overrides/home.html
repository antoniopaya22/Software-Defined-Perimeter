Software-Defined Perimeter Lab

A reproducible, CI-tested Software-Defined Perimeter built with Docker Compose. Services stay hidden behind a default-deny gateway until a client authenticates with a single encrypted packet.

Architecture

Five containers, three networks

The lab follows the Cloud Security Alliance SDP model. Every component runs pinned upstream code, and credentials are generated at runtime.

{% include ".icons/material/shield-key-outline.svg" %}

SDP Controller

Waverley Labs controller. Runs the PKI, authenticates every member with mutual TLS and pushes service and access lists.

sdp-controller
{% include ".icons/material/wall-fire.svg" %}

SDP Gateway

fwknop behind a default-deny iptables firewall. Opens time-limited DNAT and FORWARD rules per authorized client.

sdp-gateway
{% include ".icons/material/laptop.svg" %}

Initiating Host

The client. Sends SPA packets with fwknop and refreshes its credentials with the controller.

sdp-client
{% include ".icons/material/server-network.svg" %}

Accepting Host

An nginx service on an internal network, reachable only through the gateway.

protected-service
{% include ".icons/material/database-outline.svg" %}

Policy database

MariaDB with members, services and permissions, on a management network with no host access.

sdp-db

Quick start

Running in three commands

Requires Linux and Docker Engine 26 or newer. The demo script checks the whole flow and exits non-zero if anything fails; CI runs it on every pull request.

Full getting-started guide →

1
Configure secretscp .env.example .env
2
Build and startdocker compose up -d --build --wait
3
Run the end-to-end check./scripts/demo.sh
PASS service hidden before SPA
PASS private network unreachable from the client
PASS SPA accepted, controller session completed
PASS protected service returns HTTP 200
All checks passed.
