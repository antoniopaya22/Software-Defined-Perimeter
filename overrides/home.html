Software-Defined Perimeter lab

One packet
opens the door.

Services stay invisible behind a default-deny gateway. A client sends one encrypted, authenticated packet; the gateway opens a path for that client alone, for thirty seconds.

Get started Read the paper ↗
  • Published as SecureSDP in the International Journal of Information Security, 2024
  • Five containers on three networks, one docker compose up
  • Tested end to end in CI on every change
WhereIn front of any TCP service
What it stopsScans and unsolicited connections
CostOne UDP packet per session

The problem

An open port
is a target.

A service that answers everyone can be found, fingerprinted and attacked before any credential is checked. A Software-Defined Perimeter turns that around: nothing answers until the client has proven who it is.

Scanners find it

Any reachable port shows up in a sweep of the network.

Banners give it away

Versions and software leak before authentication.

Exploits come first

A pre-authentication bug is enough to get in.

Illustration of the mechanism, not a measurement.

How it works

Authenticate,
then connect.

The controller runs the PKI and the policy. The gateway drops everything and listens for Single Packet Authorization. A valid packet opens a short-lived rule for one client, one service and one address.

01

Enroll

Every member authenticates to the controller with mutual TLS; the gateway gets its access list.

02

Knock once

The client sends a single encrypted, HMAC-authenticated SPA packet with fwknop.

03

Open for one

fwknopd adds DNAT and FORWARD rules for that client's address and removes them after 30 s.

Run it

Three commands
to a dark service.

The controller creates the CA and every member's keys on first start; nothing secret lives in the repository. The demo script checks the whole flow and fails loudly if anything is off.

docker-compose.yml
sdp-gateway:
  build: ./gateway
  cap_add: [NET_ADMIN, NET_RAW]   # iptables + SPA sniffing
  sysctls:
    net.ipv4.ip_forward: "1"
  volumes:
    - type: volume
      source: bundles              # its own credentials only
      target: /bundle
      read_only: true
      volume: { subpath: "1" }
  networks:
    sdp-public:  { ipv4_address: 10.231.0.20 }
    sdp-private: { ipv4_address: 10.231.1.20 }
terminal
$ cp .env.example .env
$ docker compose up -d --build --wait

Questions.

Is this ready for production?

No. It is a research and teaching lab. The upstream SDP controller and fwknop fork are no longer actively maintained; review credentials handling and firewall rules before reusing any part of it.

Why the Waverley Labs fork of fwknop?

It adds the SDP control channel: fwknopd receives its service and access lists from the controller over mutual TLS instead of a static access.conf, and clients rotate their keys on every session.

Can I add clients and services?

Yes. Add rows to the seed data and a client service in Compose; the configuration guide walks through it.

Does the lab run Egida?

No. Egida hardens full hosts through Ansible, which does not fit containers. To reproduce the hardening results, deploy the components on virtual machines and run Egida there.

How does this relate to Secure-SDP?

Both accompany the same article. This lab runs the Waverley Labs SDP; Secure-SDP is a Go implementation of the Bridge model described in the paper.

How do I cite it?

Cite the SecureSDP article in the International Journal of Information Security 23(4), 2793–2808, 2024. BibTeX is on the paper page.
